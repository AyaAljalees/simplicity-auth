---
title: Email domains
description: Which email addresses a tenant's IdP may sign in, how a tenant proves it owns a domain, and how a domain requires SSO.
---

A tenant's settings admin configures their own IdP (`auth_domains`). An IdP can
claim any email address it likes, so the library trusts it only for the email
domains **its tenant has verified**. Without that check, a tenant admin could
point an auth domain at an IdP they run, create `you@your-company.com` in it, and
sign in as you.

## The rule

- The OIDC callback refuses an email address whose domain the auth domain's
  tenant hasn't verified. It throws `EmailDomainNotVerifiedError` (HTTP `403`,
  code `EMAIL_DOMAIN_NOT_VERIFIED`) **before** looking the user up or calling
  `provisionUser`.
- An address that passes is authoritative. The session reaches everything that
  user is authorized for, in any tenant.
- The match is exact: verifying `acme.com` doesn't cover `eu.acme.com`.
- Personal addresses (gmail.com and the like) can't use a tenant's SSO, since
  nobody can verify those domains. Those users sign in by code.

## Verifying a domain

The `tenant_email_domains` table holds each claim. A settings admin, as
`app_rls`, can:

- claim a domain: `INSERT (tenant_id, domain)`;
- set `sso_required`;
- remove a claim by setting `deleted_at`.

They **cannot** write `verification_token` or `verified_at`. Column grants leave
those out, so no write a tenant admin can make, by any route, marks a domain
verified. The token is generated by the database for each row, so a token
published by another tenant can't be reused.

The verifier (opt-in subpath `@smplcty/auth/email-domains`) proves ownership with
a DNS TXT record. You choose the record's name and value prefix, so customers
see your product, not this library:

```ts
import { emailDomainVerifier } from '@smplcty/auth/email-domains';
import { withServiceContext } from '@smplcty/auth';

const verifier = emailDomainVerifier({
  recordLabel: '_my-shiny-product', // → _my-shiny-product.acme.com
  valuePrefix: 'my-shiny-product-verification', // → my-shiny-product-verification=<token>
});

// Show the customer what to publish (from the row they can read):
verifier.record({ domain: row.domain, verificationToken: row.verification_token });
// → { type: 'TXT', name: '_my-shiny-product.acme.com', value: 'my-shiny-product-verification=…' }

// When they click "Verify": a privileged connection with an audit actor.
const verified = await withServiceContext(privilegedPool, 'domain-verifier', (client) =>
  verifier.verify(client, row.tenant_email_domain_id),
);
```

- **`verify` only records what DNS proves,** so it's safe to call on any user's
  behalf. It returns `false` until the record appears; DNS can take minutes, so
  let the customer retry.
- **It connects as `app_privileged`** (the only role that can write
  `verified_at`) with `app.actor_id` set, because `updated_by` is `NOT NULL`.
- **Use an underscore label** (RFC 8552). A bare label like
  `my-shiny-product.acme.com` is a hostname: it can collide with a real host, and
  a name that already has a CNAME can't also hold a TXT record.
- **DNS lookups use `node:dns/promises`** by default. Pass `resolveTxt` for an
  edge runtime (for example, a DNS-over-HTTPS lookup) or a fake in tests.
- **Changing `recordLabel` or `valuePrefix` later** leaves verified domains
  verified. Only pending verifications need the new record.

A global admin can verify a domain for a customer who can't edit DNS, through
the privileged pool:

```sql
UPDATE tenant_email_domains SET verified_at = now()
WHERE tenant_email_domain_id = $1;
```

## Requiring SSO

Set `sso_required` on a verified domain, and code (OTP) sign-in is refused for
every address at that domain, **on every sub-domain**: `SsoRequiredError` (HTTP
`403`, code `SSO_REQUIRED`). The router checks the identifier before sending a
code, and checks every email address of the signed-in user before completing.
So a user at that domain can't sign in by phone either.

Outsiders are unaffected. `sam@mabulu.com` isn't at `acme.com`, so they sign in
their usual way and reach Acme through whatever roles they hold.

This replaces the old per-tenant `allow_otp` switch, which blocked code sign-in
on a tenant's sub-domain for everyone, outsiders included, and missed the same
users on every other sub-domain.
